Two flaws left in the baked worlds, fixed in `ProceduralWorldDocument::BuildTexturedTerrainModel` and `RenderTerrainTexture`.

- **Shorelines.** The water was drawn per quad, so a lake's edge was a staircase of whole quads. A quad with any corner in the water now gets a flat quad at that
  water's level (a lake's fill level, or the sea's), which runs on under the dry corners; the ground hides it there, so the visible edge is where the ground
  really crosses the water level. The texture's lake and sea beds follow the same line (how far under the surface the ground is, from the highest water level
  among the four samples round a texel), so the dark bed ends where the water does.
- **The terrain's edge.** A skirt (`BakeOptions::terrain_skirt`, 6 m by default, 0 for the old open edge) carries the four edges down below the lowest ground,
  flat shaded and textured by the ground texture's edge stretched down, so the terrain is a block and not a sheet. A third primitive, using the ground's material.

Both checked in the player from two angles. The skirt's streaks are the edge texture stretched down; they read as soil strata but are not an earth texture.

Not done: an earth/strata texture for the skirt; the bottom of the block is open (nothing looks at it); only a base colour on the ground (no normal map or detail
texture); rivers are painted, so they have no surface motion or reflections; water is one flat colour with no depth tint or foam.

## Play in the editor: an error says which entity it happened on, and clicking it goes there

An error used to be a line of text in the Console, with the entity's name and the first eight characters of its GUID buried
in the sentence. That is a report, not a lead: with forty doors named "Door" in a level, "Door.luau:4" alone does not say
which one, and there was nothing to click.

The information is now data beside the text. `ScriptSystem` records an `ErrorOrigin` for every entry in `Errors()`, in the
same order: the entity's GUID, the name it had at the time, and the callback (`OnUpdate`, `OnStart`, a method called from
C++). Errors that belong to no one entity -- a class that would not load, an event handler or timer, a Blueprint -- get an
empty origin. `Game::RuntimeErrors()` pairs each text with its origin and appends the Blueprint errors (text only), and
`LiveViewport` and the Scene View's `SceneViewShading` interface carry the list to the editor. A destroy-on-error case
is handled too: an error raised while ending play for an entity already gone has no GUID to offer, and says so by having
none.

In PIE the Scene View lists the errors under its banner -- up to three rows, a red panel that clips long messages, with
"+N more -- the Messages tool lists them all" when there are more. A row that names an entity is a link: the row lights
under the mouse and a click selects the entity, so the failure and its cause are one gesture, without leaving the
viewport. The rows' rectangles are reported in `PieOverlay::errors`, so a test clicks them like a person would.

Messaging is the other half. `EditorWorkspace::Update` polls the running game each frame while the document plays and
posts the first sight of each error to the notification service as an `Error` with an `Entity` target. The key is the text
with the game's " (repeated N times)" suffix cut out and the GUID appended, so a broken `OnUpdate` that fails every frame
is one row, not a new row at each logging threshold. Messages sends its click back through the same path as every other
target: the entity is selected and the Scene tool is focused. The seen-set is cleared when the session ends, so a second
play session reports its errors again; the rows from the first stay in the history.

Tests: `SceneView_PieRuntimeErrorsLinkToTheirEntity` (rows under the banner, linked row selects, unlinked row does not,
Stop clears the panel), `EditorWorkspace_RuntimeErrorsReachMessagesWithTheEntity` (one row with the entity target, the
repeated suffix does not add rows, a new session reports again), and the origin assertions in
`ScriptSystem_ErrorsSayWhichEntityAndWhereAndDoNotFloodTheList`.

## Play in the editor: the two numbers the stats row was missing

The PIE stats row already said CPU frame time, physics bodies and script instances. It did not say how much of the
frame the scripts were, or how much geometry the picture was. Both are one number away from code that already exists.

Triangles come from the renderer's draw calls the same way draw calls do: `ICommandList` gained a `TriangleCount` beside
`DrawCallCount`, and the backends' existing `NoteDraw` now takes the triangles a draw covers -- `vertex_count / 3` for
`Draw`, `index_count / 3` for `DrawIndexed`. The indirect forms add nothing, because their argument is read on the GPU and
nothing reads it back; a scene drawn that way shows fewer triangles than it drew, which the header says. A triangle list
is assumed, as it already was for the draw counter.

Script time is measured where callbacks run rather than guessed from the frame: `ScriptSystem::CallTimed` wraps every
`ProtectedCall` for a class callback (`OnUpdate` and its siblings), an event handler and a timer, and adds the wall time to
a per-frame total. `Game::Tick` zeroes the total before its systems run and stores it in `GameStats::script_ms`, so the
number is the last frame's callbacks and nothing else -- physics and rendering time stay in the CPU and GPU numbers
beside it. The value reaches the chip through `LiveSceneShading::FrameStats`; it is negative while unknown, so
`SceneViewPanel` only prints it in PIE.

The chip in PIE now reads: entities · draw calls · triangles · GPU ms · CPU ms · script ms · bodies · scripts · FPS. While
editing it is unchanged: nothing is running, so there is no script time to report.

Tests: `SceneView_TheStatsChipNamesTheEntitiesTheDrawsAndTheFrameRate` now sets triangles and script time on its stub
shading and checks both appear in PIE and neither outside it, `ScriptSystem_TimesScriptCallbacks` checks a busy method is
measured and a reset zeroes the total, and `Templates_ThePlayerRunsThemCooked` checks the packaged game reports a sane
per-frame script time.

## Play in the editor: Simulate runs the game without taking the camera

Play hands the viewport's camera to the game: the game camera becomes the editor's eye, and Stop ejects back to where the
play started. That is right for testing what the player sees, and wrong for watching a level run while you move around
it -- the moment the game's camera starts following a character, you are no longer looking where you chose.

Simulate is Play with that one difference. The play session gained a `simulate` flag, set when the session starts from the
editing edge and cleared by Stop; Pause and Resume leave it alone, so a Simulate session stays one until it ends. Because
it is the same `PlaySession`, everything else follows without a second copy: the snapshot and its restoration, discarded
edits, the console's clear-on-play, the runtime stats and error polling, and the strip's Pause/Step/Stop.

The camera contract lives in two small places. `SceneViewPanel` reads `SceneDocument::IsSimulating()` when a session
appears and does not possess its camera, so Stop has nothing to restore and the view stays where the person moved it.
`LiveViewport::Frame` gained a `free_camera` flag: it saves the running game's camera transform and component, borrows
them to place the picture at the editor's eye for the draw, and puts the saved pair back before the frame is submitted --
the draws hold the borrowed pose, the game keeps simulating from its own camera. The Scene View's banner says it:
"Simulating — the camera is yours; edits are discarded on Stop". The workspace strip shows a grey **Simulate** chip beside
Play while editing (Pause/Resume, Step and Stop replace it while the game runs), and the status bar reads
"Simulating"/"Simulating (paused)".

Tests: `SceneDocument_SimulatePlaysWithoutOwningTheViewsCamera` (same states, same discarded edits; Resume keeps the
session simulated), `SceneView_SimulateLeavesTheViewCameraWhereThePersonPutIt` (the overlay flag, the banner, and Stop
leaving a moved camera in place), `LiveViewport_FreeCameraPutsTheGamesCameraBack` (a normal frame moves the game camera
with the view's; a free frame leaves it at the scene's own pose, twice in a row), and the workspace strip test clicks the
Simulate chip and checks the session it starts.


## The Game view: the game's camera in its own window

Every view the editor had drew from a camera the editor owned. The Scene View orbits; the Live Viewport flies; and in PIE
the Scene View's shading puts the running game at the editor's eye — Simulate only stopped it from moving the game's
camera, it did not show it. Unreal separates the two views for a reason: the Scene view is where you work, the Game view
is what the player sees, and after Play hands the camera to a character you need both at once.

The Game view is a tool window of its own. `GameViewPanel` is portable and headless-testable: it watches the play
session's edges, starts its `GameViewSurface` once per session, hands it the document's `PlayDelta` every frame (zero
while paused, one frame after Step), and lets the game go on Stop. A start that fails says why once, not on every frame
of the session; outside a session the window is black with a sentence naming Play.

The surface is `LiveGameView`: it cooks the scene as the session begins and runs it in a `LiveViewport`, and asks
`LiveViewport::FrameGameCamera` for each frame. That is a new entry point rather than a flag on `Frame`: the existing
`Frame` always places a camera for the draw, and the one thing the Game view must never do is place one. `RenderFrame`
now takes an optional pose; `Frame` passes one (and still borrows it back on Simulate), `FrameGameCamera` passes none, so
the draw uses the active Camera entity exactly as the game left it — pose, field of view, projection and all. A scene
with no camera still gets the viewport's fallback camera, so the window is never empty for that reason.

The picture keeps the game's aspect and letterboxes to the window at a fixed session resolution (1280x720 by default:
the swap chain is made with it). Paused frames are skipped below the editor (`play_dt` is zero and the last picture
stands), so a paused Game view costs nothing. The panel is registered by the shell as the "Game View" extension in the
Scene category, beside the Live Viewport.

One cleanup: the cook's asset list — the models the ModelRenderers name, and the textures and graphs the
MaterialParameters name — was copied in the Live Viewport and the Scene View's shading. With a third caller it moved to
`editor/src/host/preview_assets.h`.

Tests: seven headless ones over a fake surface cover the state machine (nothing outside a session; one start per
session; a fresh start after Stop; paused zeroes the time; Step is one frame; Simulate is reported; a failed start is
not retried per frame; no surface says the Vulkan editor is needed; the letterbox keeps the picture's aspect and is
centred). On a Vulkan device, `LiveViewport_FrameGameCameraDrawsFromTheScenesOwnCamera` checks the frame comes from the
scene's own camera, leaves it untouched, and differs from the editor's view of the same scene; and
`GameView_PlaysTheSessionFromItsOwnCamera` drives the whole panel through Play, Pause, Step, Stop and a second session
with the camera moved.
