# 2026-11-15

The visual generation editor, item 4 of the procedural-world list, as editor panels (`editor/src/world/procedural_document.h`, `procedural_panel.h`).

- `ProceduralWorldDocument` (headless, like the other documents): every setting of the terrain generator, the scatter rules, and a mesh family per rule;
  four presets (temperate, alpine, desert, islands); undo that takes one step per edit and not per slider tick; seeds and a dice button; Generate; a
  preview picture; and three ways out. `ApplyToTerrain` hands the heightmap, layers and splatmap to the Terrain editor (its sculpt tools carry on),
  `ApplyToFoliage` the instances to the Foliage editor (one undo step), and `Bake` writes files under `Content/Generated/<name>/`: the terrain as a model with
  six surfaces, a `.glb` per mesh variant, and an `.ascene` with the terrain and the scatter as model entities, which the player loads.
- `ProceduralWorldPanel`: tabs for Terrain (sliders with tooltips), Scatter (rule list, per-rule editor, mesh family) and Output; regenerates as you edit when
  the last generation was quick, once the edit settles. Registered in the workspace under World.
- The terrain module is not in the player (no terrain component or asset type; the MCP terrain tools say so too), so a bake exports the terrain as a mesh. That is
  why the output is a model and not a terrain asset.

Rendering a baked world in the player found three defects in the generator that the tests had not. Hydraulic erosion made the terrain spiky: it raised the mean
|laplacian| from 0.06 m to 0.47 m, and the cause was the sediment capacity (4, the usual figure for a 0..1 height range, carries metres per droplet on a 60 m terrain);
0.5 leaves it at about 0.11 m and still cuts gullies, and the erosion now digs over a disc and not one cell. Lakes drew on their bumpy beds (a flat surface at each
lake's fill level now, and at the sea level for the sea). A 3x3 smoothing stage (`smoothing`, default 2) was added first as the suspected fix; it barely changed the
roughness (the noise was not the cause) but it is kept as a setting.

Not done: grass, shrubs, reeds and cacti have no mesh generator, so their rules are scattered and shown in the preview but baked as nothing; the terrain's biome
borders are stair-stepped (one surface per quad); the terrain edge is an open lip; a baked scene is one draw call per object (the RHI has no instancing), capped at
5,000 objects by default; no node graph; the terrain's textures are single colours.

## Content browser: multi-select and the batch operations (parity stage 3)

The Content Browser's listing now keeps a selection and acts on all of it at once (`editor/src/content/content_browser_panel.{h,cpp}`).
Click selects, Ctrl toggles, Shift takes the range from the anchor in the current listing, and a rectangle dragged over the grid's
tiles takes every tile it touches (Ctrl+drag adds); Delete, Ctrl+D, Ctrl+A, F2 and Escape work while the listing has focus, and the
selected tiles get an amber border. Duplicate, Delete and Move run over the whole selection as one batch: the new
`assets::DuplicateContent` and `assets::DeleteContents` (`engine/src/assets/content_browser.cpp`) and `MoveContent` per path, then a
single rescan and a single refresh. The engine header's `DeleteContents` reports how many entries it removed, and that number is 0
on refusal -- a delete is all-or-nothing, refused while anything outside the batch refers to something it would remove, with the
users named in the error. Duplicates are named "<stem> copy", "<stem> copy 2", ... with fresh GUIDs and no sub-assets or source
hash, so the copy imports on first use; the copies become the selection, so duplicating again continues from them. Rename happens
in place on the tile or row (`BeginRename`/`RenameEntry`): a name with no extension keeps the asset's, a changed extension is refused
because it would change the type, and renaming the folder being shown keeps it open. The toolbar gained a Create menu that makes one
asset of any registered type (`ExtensionRegistry::CreateAsset`) and starts its rename, plus Duplicate, Delete and the selection
count; the listing's background menu offers Select All, Create, Duplicate and Delete. The transaction is the batch rather than an
undo step: the asset database has no undo, and a file move cannot be represented in the ECS command stack.

Tests: `tests/test_content_multi_select.cpp` -- duplicate finds free names and fresh identities (folders too) and refuses pieces,
meta files and paths outside Content; a delete batch is refused whole while a model outside it uses one of the textures and removes
nothing, then takes the folders once the references are inside it; selection extends, toggles, selects all, clears, and a rectangle
selects the tiles it touches (and only those); duplicating selects the copies and numbers them; deleting through the panel refuses
the batch or takes all of it and already lists the result; moving the selection and the open folder follows it; rename keeps the type
and the selection. The remaining Stage 3 items are the filter chips/folder scope/breadcrumbs/sortable columns/`type:`/`path:` search,
the import settings drawer with reimport and Explorer drag-import, an opener for every asset type, the reference viewer upgrades, and
Reveal in Explorer / copy path.

## Content browser: the search grammar, the type chips, the folder scope and the columns (parity stage 3)

The Content Browser's listing can now be narrowed (`editor/src/content/content_browser_panel.{h,cpp}`,
`engine/src/assets/content_browser.cpp`). The search field takes a small grammar instead of one substring: whitespace
separates words, every word has to match, a `type:` word matches the importer's name and a `path:` word the content path,
all as lowercased substrings -- "crate type:Model", "type:tex" and "path:props/ type:Texture" -- while plain words still
match the name, so every old query means what it did. A word whose value is empty ("type:") is not a term; with no terms
left the search is not a search and does not widen the scope to the subtree. The parse lives in `ListContent`, so the
grammar is the engine's, not the panel's, and a host asking the same query gets the same answer.

The panel's side is UI state and filtering. A chip row under the toolbar lists every importer present in scope with how
many entries it has before the chips apply; clicking one keeps only that type, clicking again drops it, "All" clears the
list. A selected chip stays listed at 0 when a search leaves nothing of its type, because otherwise the chip that caused
the empty listing would be the one thing not on screen to switch off. "Subfolders" sets the scope to the whole subtree,
and the "3 of 12 items" count uses what the scope and the search leave as the denominator, so it describes the chips and
Changed only rather than the scope. The "Content/Models/Crate" line under the toolbar is now a breadcrumb: the current
segment is text, every other one navigates, and "(with subfolders)" says when the listing includes them. The list view's
Name and Type headers sort, with `^`/`v` on the sorted one, a second click flipping the order, and folders first under
either column (still by name when descending). Ctrl+F focuses the search field. An empty narrowed listing says "No
entries match." and offers Clear filters instead of claiming the folder is empty; folders are never hidden by the type
chips, only by Changed only, which is what the VCS test expects.

Tests: `tests/test_content_filters.cpp`. The grammar: `type:model` returns the four glTF models, case-insensitive
`TYPE:TEX` the four textures, `path:textures/` the same four, `path:models/ type:model` the models, and "checker
type:texture" / "cube type:model" narrow to the two checkers and the one cube; "test cube" and "model cube" show that
every word has to match; "type:" and "path:" show that an empty directive is not a term and the folder's own listing
comes back. The panel: chips count the scope (4 models in `models/`, 4 + 4 with subfolders), a chip and a search narrow
together and the chip recounts what the search left, a chip whose type is gone is still listed at 0, Clear filters
restores the listing, the "of" count stays at the scope's total, and a nondescript headless frame draws the chip row,
the no-match line, the breadcrumbs and the sortable headers without tripping an ImGui id clash. Sorting: by Type puts
Model before Texture and flips with descending, folders stay first under both columns, and descending by Name inside
`textures/` starts at `test_solid_red.png`.

## Content browser: import settings, reimport and files dropped from Explorer (parity stage 3)

Import settings live beside the asset, not in the panel, so the panel now has the two functions that write and read them:
`assets::ImportSettingsFor` answers what an asset would import with (the importer's defaults with the `.ameta`'s choices
merged over them, exactly what `ImportAsset` uses), and `assets::SetImportSettings` validates and stores a change. A
change is checked against the importer's own defaults -- an unknown key is refused (`The Texture importer has no setting
"quality"`), and so is a value of the wrong JSON kind (`"srgb" must be a boolean, not a string`) -- because the drawer
and the `.ameta` editor would otherwise disagree about what a typo means. Writing settings clears the `.ameta`'s recorded
source hash, which is what the next `Scan` turns into `needs_import`: there is no separate flag to forget, and `MarkImported`
puts the hash back. Sub-assets are refused with a pointer to their source, since their options are the source's.

The drawer ("Import Settings", opened from the toolbar or an entry's menu) draws one widget per setting -- Checkbox,
InputInt (clamped), InputDouble, InputText; anything else says to edit the `.ameta` -- and has Apply and Reimport, Reimport,
Defaults and Close. Apply writes the settings and imports at once; Reimport alone re-runs `ImportAsset` with the project's
importer registry and `Intermediate/DDC`, which is also the path the context menu uses. That menu entry is deferred
(`Pending::Reimport`) because a reimport re-registers sub-assets and rebuilds the rows while `DrawRows` is walking them.
A reimport that is a cache hit says so ("Reimported x.png (from the cache)") instead of pretending work happened.

Dropping files from Explorer is `on_files_dropped` on the window: a `std::function` the platform calls synchronously from
`PumpMessages`, filled by `WM_DROPFILES` (after `DragAcceptFiles`) in the Win32 window and by `glfwSetDropCallback` in the
GLFW one -- so the engine itself still copies and opens nothing. The shell passes the paths to
`EditorWorkspace::ImportDroppedFiles`, which hands them to `ContentBrowserPanel::ImportFiles`: it plans the whole batch
first (every entry a regular file whose extension `ImporterForExtension` maps to an importer, no directory), then, for a
name that already exists, compares `HashFile` -- identical contents are selected without a copy, different contents refuse
the batch by name -- then copies each file (the scan writes its `.ameta`) and rolls the copies back if a write fails. The copies
become the selection and the browser refreshes once; the workspace focuses the Content Browser and posts one notification
(how many landed, that they were already there, or why the drop was refused) so a drop that does nothing still says so.

Tests in `tests/test_content_import.cpp`: `ImportSettings_RoundTripAndReimportIdentity` (defaults; a first import of seven
mips, then `{srgb:false, generate_mips:false}` clears the hash and marks it, and the reimport is one non-srgb mip; a cached
reimport is byte-identical; `{}` restores the original bytes from the cache; refusals leave the stored settings alone; a
`.luau` script has nothing to configure), `ImportFiles_CopiesIntoTheOpenFolderAndSelects` (copy, select, `needs_import`;
a second drop copies nothing; a refused batch copies nothing; a directory is refused; a different-contents collision is
refused and the original is untouched; a drop into the root works) and `ImportSettings_DrawerEditsAppliesAndDraws` (the
drawer's state, a wrong-kind error keeps it open, Apply persists and clears `needs_import`, Reimport is a cache hit,
folders/scripts/missing files are refused, and two headless frames draw the window).

## Content browser: an opener for every asset, the reference viewer's clicks, reveal and copy path (parity stage 3)

Double-clicking an asset used to be the plugin registry's business alone, so a `.amat` or a `.aanim` did nothing. Now
`ContentBrowserPanel` has a host opener (`SetAssetOpener`) and asks it first; the workspace installs
`EditorWorkspace::OpenAsset`, which is also public so a menu or a test can open a content path directly. It switches on
the extension and loads into the tool's open document, which keeps one document per kind (the tabs, the undo history and
the panel's own state stay the same object): blueprint, material, animation graph, blend space, sound cue, UI layout,
behavior tree, particle system, sequence, scene, and `.luau` text. Two gaps had to close for that: `BlendSpaceDocument`
had no `Load` (only save), and the scan did not know `.amat` or `.abt` at all -- they are `Material` and `BehaviorTree`
in `ImporterForExtension` now, so the Content Browser lists the graphs the editor itself writes.

That first version of the importer change broke a live viewport test, and it was worth the failure: a material graph names
its textures as asset GUIDs inside the file, which is why the cook has a special case for `.amat` roots -- a file no
importer claims is carried as it is, and its textures are followed by GUID. A `.amat` is an asset now, so it took the
ordinary asset path instead: cooked as a `Material` record with no dependencies, its textures left out of the package,
and `LiveViewportPanel_AMaterialGraphIsDrawnInPlaceOfTheModelsSurface` drew the model's own surface instead of the
graph's blue. The fix is in the scan rather than the cook: `RebuildDependencies` scans a `Material` like a scene, finds
the GUIDs its parameters hold, and records them, so the texture cooks with the graph. A regression test in
`tests/test_asset_database.cpp` (`AssetDatabase_AMaterialGraphsTexturesAreDependencies`) pins it.

A failed open has a reason. No extension claims it: "No editor opens x". A registered type has no opener: "Dialogue
assets have no editor (x)". A file of a known kind that does not load: the loader's own message. Every one is posted as a
"No editor" warning in Messages as well as returned, so a double-click that opens nothing says so instead of doing
nothing; `LastOpenError()` keeps the text for the panel. A document with unsaved changes is refused rather than replaced.

That guard exposed a papercut worth fixing: the sample documents each tool starts with are built by edits, so `Dirty()`
was true before the user touched anything, and every open was refused. The five documents that seeded themselves this way
(animation graph, blend space, sound cue, UI layout, behavior tree) gained `MarkSaved()` -- dirty flag and undo history
cleared, revision bumped -- and the workspace calls it once after building the tools. The samples are an initial state,
not unsaved work; a later edit still refuses the open.

The context menu's Copy Path and Reveal in Explorer are host-callable too (`CopyPath`, `RevealInFileManager`), because the
menu is hard to drive headlessly and because a shell's own menu wants the same action. Copy Path records the absolute path
in `LastCopiedPath` and puts it on ImGui's clipboard; Reveal hands it to the workspace's `SetRevealer`, which runs
`explorer.exe /select,<path>` on Windows, `open -R` on macOS and opens the parent folder elsewhere -- a host with no file
manager has none installed and the menu item is disabled with a tooltip saying so. The reference viewer now has
Dependencies and Find usages (referencers) as radio buttons that re-walk the graph in place (`ShowReferences` opens it
without the menu), and every row is a `Selectable` that calls `ShowEntry` -- select the asset, show its folder. The
validation list's rows do the same, which is what turns the broken/missing list into something to act on.

Tests in `tests/test_content_openers.cpp`: `Openers_EveryOpenableKindLoadsItsFileAndShowsItsTool` (one file per kind,
written with that kind's own serializer, each open true and its tool selected and popped out, no refusal posted),
`Openers_SayWhyAnAssetCannotOpen` (unknown extension, missing file, a file that does not parse, a type without an opener,
a dirty scene), `Openers_ThePanelUsesTheHostOpenerAndFallsBackToTheRegistry` (the registry's no-opener message and the
host's own reason winning), `Openers_CopyPathRevealAndTheReferenceViewer` (dependencies and referencers both ways,
`.amat`/`.abt` in the listing, a missing source in the validation list, the windows drawn headless, Copy Path and a
recorded reveal) and `Openers_EveryRegisteredTypeWithAnOpenerOpensHeadless` (the `.astrings`, `.asav` and `.asettings`
openers the workspace registers).

## Tilemaps and tilesets open in the tilemap editor (parity stage 3)

The tilemap tool existed but nothing could feed it a file, so a double-click on a `.atilemap` still did nothing. Two
things were missing. `TilemapEditDocument` could save to a pair of paths but never load from them and never remembered
them, so it gained `Load` (map and tileset together, replacing what is open and clearing the history) and a no-argument
`Save` for the files it was opened from or last saved to -- a sample that has never been saved says exactly that. The
panel's header now shows the map's file name next to its size, so an opened map is not mistaken for the sample.

The opener itself is a small piece of content-path arithmetic: a tilemap stores its tileset as an asset GUID, so
`EditorWorkspace::OpenAsset` reads the map, finds the tileset record in the Content Browser's database, and loads the
tileset from its current path -- a moved tileset still opens, and one that is gone is named as the reason. A
`.atileset` has no window of its own, so opening it opens a tilemap that uses it (found through the asset database's
referencers) and says "No tilemap uses ..." when none does. The dirty guard is the same as the other kinds: painting a
cell and then double-clicking another map is refused until the tilemap is saved.

Tests in `tests/test_content_openers.cpp`: `Openers_TilemapsAndTilesetsOpenTheirEditor` (the map loads with its layer
and cell, the tileset opens its map, an unused tileset and a map with an unknown tileset are refused by reason, and a
painted edit is both refused and written back by `Save`).
