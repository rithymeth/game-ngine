# 2026-11-16

Four plant generators in `engine/include/aether/assets/procedural_mesh.h`: `GenerateShrub` (leaf masses on thin stems), `GenerateGrass` (two-sided tapering
ribbons, flat shaded), `GenerateReeds` (stalks with cattail heads) and `GenerateCactus` (a column with a rounded top and up to four arms), as kinds Shrub, Grass,
Reeds and Cactus for `GenerateVariant`. The Procedural World editor's starter rules now all have a mesh family (the user's own added rules still start with none),
so the shrub, grass, reed and cactus rules bake instead of baking as nothing.

A bake's object budget used to be spread evenly over every instance, which with a grass rule of 40 tufts per 100 square metres would have thinned the trees by
the same factor as the grass. It follows the scatter's pecking order now: earlier rules (trees) keep every instance while there is room, and the grass is
thinned to what is left. A test holds it (all pines survive a budget that grass would have eaten).

Checked in the player: a gallery of every plant up close (shrubs, grass tufts, reeds and cacti read correctly), and a re-baked Temperate world with 3,000 objects.
The tufts are about 0.5 m, so they only show up close; that is the scale of grass.

Not done: a flower or bush variant with colour, grass that sways (no wind in the shader), LODs or impostors for the 3,000-object scenes (one draw call each),
and a grass card with a texture (the generator has no textures).

## Copying a whole component (parity stage 4)

The Inspector could already copy, paste and reset one property; the component card itself had only "Remove Component"
on a right-click nobody would guess. Every component header now has a «...» button at its right edge (right-clicking the
header opens the same menu) with Copy Component, Paste Component Values, Reset Component, Revert Component to Prefab and
Remove Component, acting on one entity or on the whole selection.

The component clipboard is its own, apart from the single-value one, typed by the reflected type and owning its copy,
so Paste is offered only on a component of the copied type and later edits at the source do not leak into it. Paste and
Reset write every field the Inspector shows — read-only fields included, because a read-only field is kept in step
with an editable one (a model's path with its asset) and pasting one without the other would split them — and never a
hidden field, which is runtime state. Each field that differs anywhere becomes one `SetFieldOnEntitiesCommand` carrying
every entity's own old value, grouped in one transaction: one undo step puts each entity back the way it was, and a
paste into a prefab instance records an override for each field it actually changed, as typing would have. A selection
where one entity lacks the component is refused whole rather than half applied, and an action that changes nothing
records nothing.

Tests: `tests/test_component_card.cpp` (5). Not done: reordering cards (the ECS keeps no per-entity component order to
move a card within) and the multi-selection screenshot gate.

## Dragging several entities in the hierarchy (parity stage 4)

The hierarchy could select several entities, then delete, duplicate or rename them together, but a drag still carried
only the row under the mouse. Worse, it could not carry more: pressing a selected row collapsed the selection to that
row on the press, before any drag could start. Now a press on a selected row of a multi-selection waits until release.
If it was a click, the selection becomes that row as before. If it became a drag, the selection stays and travels.

The entity payload is now one or more `Entity` values back to back. A drop on a row or on the heading reparents all of
them in one transaction ("Parent 3 entities", "Move 3 entities to the root"). An entity whose ancestor is also carried
is left under that ancestor, so dragging a parent together with its children moves the subtree intact instead of
flattening it under the target. An entity that would go under its own descendant is skipped, and the status line says
how many were skipped. The others still land rather than the whole drop being refused. "Move to the scene root" in the
row menu acts on the selection the same way Delete does.

Tests: `tests/test_hierarchy_drag.cpp` (6), two of them real ImGui drags: one from a selected row, and one click that
must still collapse the selection. Not done: an above/below drop indicator. Siblings are ordered by name, so there is no
order for a drop to choose.
