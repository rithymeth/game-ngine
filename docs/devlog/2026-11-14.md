Procedural mesh generator, item 2 of the procedural-world list: `engine/include/aether/assets/procedural_mesh.h` (engine layer, so every
module can use it). It makes the engine's own `MeshData` (one primitive per material), so a piece cooks, draws and saves like an imported model.

- `MeshBuilder`: triangles, boxes, tubes with parallel-transport frames, icospheres; smooth normals welded by position (a UV seam does not crease)
  or flat; tangents from the UVs.
- Generators: `GenerateRock` (icosphere pushed by 3D fractal noise, planar cuts for split stone, flattened bottom, sits on y = 0),
  `GenerateCliff` (a displaced face with strata ledges, closed to a back plane at z = 0 so it stands against a slope), `GenerateTree`
  (pine tiers; broadleaf and dead trees by recursive branching, leaf masses at the twig tips; scaled so the tip is exactly `height`),
  `GenerateBuilding` (bays and floors, windows with panes and trim, a door, gable or flat roof, chimney), `GenerateModular`
  (wall, pillar, arch, stairs).
- `GenerateVariant(kind, index, seed)` draws every parameter from the kind's own ranges: 300 variants of rocks, pines or broadleaf trees are 300
  different meshes (a test hashes them). `ValidateMesh`, `ComputeStats` (signed volume, open edges) and `EncodeGlb` (read back by the engine's own
  glTF loader in a test).

height and averaged 22,000 triangles (up to 67,000). They are fitted to the requested height now and average 5,300 (at most 9,500); a per-kind
triangle budget is part of the test. 600 pieces generate in about 0.8 s.

two paths apart: the under-cap model is picked by its triangles, so a ray through the hole is a miss however the box reads, and the over-cap model
is picked by its box, so the same ray hits. Ten picks over the solid grid are timed: 1.3 ms each on an idle machine (2.1 ms with the gate running
four jobs) in a RelWithDebInfo build, against a 250 ms budget (2,500 ms under a sanitizer) chosen wide enough for a busy runner and narrow enough
that a superlinear triangle loop -- minutes at this size -- fails. PERFORMANCE.md gains the measurement, and the audit's cost table now says the pick at the cap is measured and guarded by a test.

Editor, Stage 3 of [the parity audit](../design/EDITOR_PARITY_AUDIT.md), the Content Browser's grid of thumbnails. The listing opens as a
grid of 96 px tiles: a picture for textures and materials from the existing `AssetThumbnail` API, and for everything else -- models,
scripts, scenes, folders -- the importer's colour with the name's first letter, so the grid reads by shape and by colour before a single
thumbnail exists. A tile carries what a row carried: the git badge (a coloured border and the letter), the drag payload, the context menu
(rename, move, new subfolder, references) and the folder drop target. Grid/List in the toolbar switches back to the rows. The pictures are
`ThumbnailStore` (`editor/src/content/thumbnail_store.{h,cpp}`), and its job is to make a folder of new textures cost frames, not seconds:
one worker thread owns its own importer registry and derived data cache and a copy of the asset database (importing registers sub-assets,
and the panel keeps reading the database it scanned), renders pictures one at a time, and hands them back through a queue the panel pumps
once a frame. Each picture is written to `Saved/Thumbnails/<guid>-<key>.png` through a temporary file, and the older key for that asset
is removed, so the folder holds one copy per asset rather than one per edit. The key is the source file's size and modified time, the
`.ameta`'s import settings, the importer name and the dependencies' source hashes -- deliberately not the `.ameta`'s timestamp: every
import, cache hit included, rewrites the sidecar's source hash, so a timestamp key would make every asset render twice and then settle.
A later open decodes the PNGs on the UI thread instead of importing, and three counters -- `Rendered`, `LoadedFromDisk`, `WithoutPicture`
-- make the difference observable. Tests: the list asks for no picture; the grid renders one per texture and writes one file each; a fresh
panel on the same project decodes all of them from disk and renders none; changing one source renders exactly that one and replaces its
file; and models are counted as picture-less and write nothing. The rest of Stage 3 -- selection, operations as one undo step, filter
chips and search syntax, the import settings drawer, openers, reference upgrades, reveal/copy path -- is still open.
