# Aether Engine v0.30.0

A rendered, editable viewport inside the editor; worlds you can generate, play and film; and the player calls a game actually needs.

The headline is the **Live Viewport**: the editor now runs the project's scene under the real renderer, and lets you select, drag,
drop, undo and edit in that picture. It started the cycle as a window that needed a full scene reload for every change; by the end, a
move, a light or material edit, a physics body and an object added or deleted are patched into the running game in place, and undo
and redo are patched too, so physics and scripts keep their state. Building it turned up and fixed two real editor defects, one of
them a save that could overwrite the project's Main scene without a word.

Around that, scripts gained the verbs a game needs (play and control a sound, shake the camera, load another scene), the installer
was rebuilt after a report that it installed nothing, and the procedural world work produced terrain, scatters, plants, water,
wind and weather that bake into a playable level. The player also stopped drawing what the camera cannot see and stopped doing
per-entity work it can do once.

## The Live Viewport

The editor has a **Live Viewport** tool: the project's scene running under the real renderer inside the editor itself (the
player's `Game` and `SceneRenderer` on the editor's own Vulkan device, an offscreen swap chain read back every frame), with the
Scene View's orbit camera. **Start** cooks the models the open scene uses and hands the running game the scene **as it is open**
(`GamePackage::SetContentOverride`, with the scene serialized the way Play-in-Editor snapshots it), so the scene does not have to
be saved first and nothing is ever written over the project's scene file. **Reload** cooks and loads again.

The game's world is frozen by default so the picture is the scene as authored; **Run game** lets physics and scripts run. After
Start, the viewport watches the document's revision and reloads a moment after every change (a drag in progress is announced
separately, so it does not reload on every frame). A model added since the last cook is named in the toolbar and appears after
**Reload**.

The Live Viewport also takes the Scene View's tools: click an object in the rendered picture to select it (ctrl adds or removes),
drag a gizmo handle to move, rotate or scale it (W, E, R, with snapping), and the selected object is outlined, all drawn over the
real renderer's picture and following your drag. The tools are one shared piece (`ViewportTools`) used by both views, so they
behave the same.

### Changes are patched into the running game

Every change used to load the whole scene again, so with **Run game** on, dragging an object restarted physics and scripts on
every frame of the drag. Each kind of change is now applied to the running scene directly:

- **Transforms** (a gizmo drag, a nudge, a typed position) go in by entity ID (`LiveViewport::PatchTransforms`) and nothing else
  is touched; the game keeps its own state. An edit costs about 77 ms instead of about 116 ms at 960x540 with 2,000 entities.
- **Components** the document names as set (`SceneDocument::TakeComponentEdits`) are copied just for those entities
  (`LiveViewport::PatchScene`): a light's colour, intensity or shadows, the sky's, the wind's, a post-process volume's or a
  decal's settings, and a `MaterialParameters` edit, all show at once without restarting physics or scripts.
- **Objects added or removed** (a model, a light, an empty, a duplicate, a dropped model, a prefab instance) are found by
  comparing the document's entities with the ones the viewport last saw, so an object the game made by itself (a script spawning
  a coin) is left alone. A patch costs about half a millisecond at 2,000 entities, against about 17 ms for the reload alone.
- **Physics bodies** keep in step on every physics step: a collider or rigid body added, changed or deleted (box, sphere,
  capsule, convex or mesh) appears, is rebuilt or goes away on the next step. While **Run game** is off the world is frozen and
  bodies are made when you turn it on.
- **Cameras** are found in the world every frame, like lights, so adding, removing or editing one needs no reload (the viewport
  draws with its own camera, so the edit does not change what you see). A script is made and ended as its component comes and
  goes, so adding or removing one needs no reload either, and editing one restarts that script alone.
- **Reparenting** an object in the hierarchy, and undoing or redoing that, is patched like any other edit: the object follows its
  new parent at once and the game keeps its state.
- **Undo and redo** are patched like the edit they reverse, including one undo of several edits grouped into a step.

What the running game sets up once when it starts is still not added or changed live: an entity with a script (whose component
is edited or moved under another), a character controller or an audio source loads the scene afresh. With **Run game** on,
editing one thing no longer puts other moving bodies back where the scene has them.

### What building it found

- **Saving could replace the wrong scene.** A new, untitled scene saved to the default name (`Scenes/Main.ascene`) overwrote the
  project's real Main scene without a word, and the Render and Start buttons save first, so pressing them in a project did it. A
  save now never replaces a file that exists and is not the open scene: it is refused with a message, and only choosing Save As
  again on that name (or opening the scene first) goes ahead.
- **The Scene tool could not open a template project's scene.** Components of the other modules (a `SkyLight`, Blueprint
  instances, colliders, scripts) were not registered in the editor process, so the scene was refused (correctly, since dropping
  them would lose data on save). The editor now registers every built-in component when it starts (`RegisterEditorComponents`).
- **Top-down BMPs were refused.** A BMP with a negative height (as the player writes its screenshots) was reported invalid by
  `DecodeImageFile` and `DecodeImageFromMemory`, because stb reports that height negative. It loads now, rows in the right
  order. Found while adding the editor's **Render Preview**, which draws the open scene with the real renderer.

## Selecting, dragging and dropping in both views

**Click anywhere on a model to select it.** Picking was by an entity's origin (a click had to land within 14 pixels of it), so a
big model could not be picked by clicking on it. Both views now read each model's bounding box from its glTF file
(`ModelBoundsCache`, kept until the scene is opened or the view is restarted) and pick by a ray through the mouse: the nearest box
the ray passes through is selected, and an entity with no model is still picked by its origin. The selection outline is the
model's real box instead of a one-metre cube.

**Click on the shape, not the box.** A box is still not the model, so the click is now tested against the model's triangles: the
gap between two pillars that share a box, or the empty corner of an L, is not the model, and a model behind the gap is what you
get. The nearer of two is judged where the click meets the shape, not where it enters the box. Limits: it uses the model's
unposed (bind) geometry, so an animated pose or an alpha-cut leaf is picked as its solid mesh, and a model of more than 300,000
triangles is still picked by its box. An object is also still selected by clicking near its origin, and its outline is its box.

**Move and rotate along an object's own axes.** The Move arrows and Rotate rings can follow the object's own axes instead of the
world's: the World/Local button in the viewport toolbar, or Q. A rotated object can now be pushed along its own length with one
arrow. With snapping on, Local snaps the distance moved (the world grid does not line up with a tilted axis). World is the
default.

**Drag across a plane.** The Move gizmo has three small squares between its arrows: grab one to slide the object in two directions
at once (along the floor, for example) in one drag. They follow the World/Local choice, snap each direction on its own, and are
one undo step. A press right on an arrow still takes the arrow.

**Drop a model or a prefab** from the Content Browser into the Scene View and it is placed on the ground under the mouse, selected,
as one undo step. A prefab (`.aprefab`) brings the crate and everything under it and stays linked to the prefab asset, so later
changes to the prefab reach it; a placed prefab takes the drop position only, not the prefab's own rotation or scale. A prefab
that cannot be read, or a path outside the content folder, says why and changes nothing. The Live Viewport takes the same drop
(rounded to the move step when Snap is on, with a ring marking where it will land while you drag) and shows the result a moment
later without reloading the scene. Dropping onto an entity in the hierarchy places it under that entity at its origin (so it
follows the entity); dropping onto the "entities" heading places it at the root.

**Drop an asset onto a path field.** A field that holds an asset path takes it from the Content Browser: a picture onto a decal's
texture, a sky light's environment image or a material parameter's texture, or a material (`.amat`, `.amati`) onto a material
parameter. The path is set as one finished edit. A field takes only the kinds it names, and a plain text field such as an entity's
name takes nothing. A model can also be picked from the Inspector's model dropdown, and the path the game loads follows it in the
same undo step. Developers: `Meta::asset_extensions` on a reflected string field says what it takes.

## Scripting the game

**Scripts can play and control sounds.** `Audio.PlaySound2D(cue [, volume_db, pitch])`, `Audio.PlaySoundAtLocation(cue, x, y, z
[, volume_db, pitch])`, `Audio.SetBusVolume(bus, volume_db [, fade])` and `Audio.StopAll()` act on the game's active audio system,
the one the Blueprint audio nodes use; with no audio system running the calls return false and do nothing. For sounds a script
wants to control, `Audio.Play2D(cue [, volume_db, pitch])` returns a handle (a number, `false` if the cue is missing or no audio
runs) that `Audio.Stop(handle [, fade_seconds])`, `Audio.IsPlaying(handle)` and `Audio.SetVolume(handle, volume_db)` take. Music
and loops are the use: start a loop, fade it out when the mood changes.

**Camera shake.** `Camera.Shake(amount)` adds trauma (0 to 1; 0.2 a bump, 0.5 a hit, 1 an explosion) to the player's camera shake.
The shake grows with the square of the trauma and drains away; it is a smooth, deterministic wobble in position and
pitch/yaw/roll. The game applies it after each frame's scripts and takes it off before the next, so a script that sets the camera
is undisturbed, and the renderer, shadows and audio listener all see the shaken camera. C++: `player::CameraShake`
(`Game::Shake()`), with `Settings` for amplitude, angle, frequency and decay.

**Scripts can load another scene.** `Scene.Load(path)` moves the game to another scene (a door into an interior, fast travel, a
region gate); `Scene.Current()` names the running one. The swap happens at the start of the next frame, so the script that asks is
not torn down under itself. A path the package does not have returns false and changes nothing; a scene that is there but does not
parse leaves the current one running with a warning. `Scene.Load(path, spawn)` takes the name of an entity in the new scene: the
player (the entity with a `CharacterMovement`) starts there, so a door can put you on its far side. C++: `Game::RequestScene`.

**`aether_player --report` now reports the speed of the run**: CPU frame time (average, p50, p95, p99, max) and, on devices that
can time the GPU, the GPU's time by stage (shadows, scene, post). The first 30 frames are left out so shader creation does not
skew it. Run it on the target hardware: numbers from a software Vulkan device say nothing about a real GPU. C++:
`player::FrameReport`; `AETHER_PLAYER_GPU_TIMING=1` prints the GPU time by stage each frame.

## Materials

A **`MaterialParameters` component** on an object (add it in the inspector, or set it from a Blueprint with Set Scalar, Vector or
Texture Parameter) now changes how the player draws it. `BaseColor`, `Metallic`, `Roughness`, `Emissive` and the textures
`BaseColorTexture`, `NormalTexture`, `MetallicRoughnessTexture`, `OcclusionTexture` and `EmissiveTexture` (the content path of an
image) replace the model's own value for that object alone, in the game and in the Live Viewport, where an edit shows at once
without a reload. The metallic-roughness image multiplies Metallic and Roughness as in glTF (set both to 1 to let the image
decide), and the emissive image multiplies the Emissive colour.

**Material graphs** are drawn too. A graph (`.amat`) of constants and parameters, opaque and default-lit, supplies base colour,
metallic, roughness, occlusion and emissive through its own shader; a graph that samples textures is drawn up to four textures
(read as the graph says, with no colour-space decode), and the cook carries a graph's textures when the graph is on the cook list.
A graph the renderer cannot draw yet (textures beyond that, translucency, other shading models, vertex offsets) says so under the
Live Viewport's toolbar and shows the model's own surface. A **material instance** (`.amati`) is drawn like its graph, and an
object can give a graph its own value for a parameter by name in its Material Parameters (up to six values of float data per
graph; past that a parameter is fixed in the shader and the viewport says so). Saving a graph or the parent of an instance shows
in the Live Viewport on the next frame, without **Reload**, and so does assigning a newly saved graph; its textures still need a
reload. Fixed: a graph with two textures lit its surface with the second as a normal map.

## Procedural worlds

A new World panel, **Procedural World**, exposes the whole pipeline as sliders with a live preview, four presets (temperate,
alpine, desert, islands), a seed box and dice, undo, and a mesh family per scatter rule. **Apply** sends the generated terrain to
the Terrain editor and the scatter to the Foliage editor; **Bake** writes `Content/Generated/<name>/` with the terrain as a model,
a `.glb` per mesh variant and a scene of model entities the player loads.

- **Terrain generation.** `aether::terrain::GenerateTerrain` builds mountains and valleys (domain-warped fractal noise blended
  with ridged noise), erodes them (thermal slides, then hydraulic droplets that conserve what they move), fills depressions into
  lakes, cuts rivers where enough water collects, and classifies biomes (water, beach, desert, grassland, forest, rock, snow)
  from height, slope, moisture and temperature. `BuildTerrainSplatmap` makes the four-layer weights (grass, rock, sand, snow) and
  `RenderTerrainPreview` draws a shaded biome picture. Same settings and seed, same terrain. About 700 ms for 513 x 513 with
  200,000 droplets, single-threaded.
- **Environment scatter.** `aether::terrain::Scatter` places trees, shrubs, grass, rocks and debris by rules: biomes, height,
  slope, distance from water, a patchiness noise, density, clumping, scale, tilt to the ground, and the footprint each object
  keeps clear of later rules. Deterministic from the seed, each rule with its own stream; about 44,000 instances in 38 ms on a
  513 x 513 terrain.
- **Procedural meshes.** `aether::assets::procedural` generates rocks, cliff faces, pine, broadleaf, dead and oak trees, houses,
  towers, and modular walls, pillars, arches and stairs from parameters and a seed, as `MeshData` with separate primitives and
  materials. `GenerateVariant(kind, index, seed)` makes a different piece per index; a pine is about 400 triangles, a broadleaf
  about 5,000, a rock 300 to 1,300. Shrubs, grass tufts, reeds and cacti were added with the same API. `EncodeGlb` writes a
  `.glb`, and 600 pieces take about 0.8 s.
- **A real oak.** `ProceduralKind::OakTree` (and `TreeParams::crown_spread`) makes a short, thick-trunked tree whose limbs reach
  sideways before they rise; across 12 variants its crown is 1.58 times as wide as tall against the birch's 1.31
  (`ProceduralOakIsABroaderTreeThanTheBirch`). It is a new kind, appended, so existing documents keep theirs.

### The baked world

A bake now produces a playable place rather than a flat picture:

- **Textured ground.** `terrain::RenderTerrainTexture` colours the terrain by height, slope, moisture and temperature with smooth
  blends (rivers blue, lake and sea beds dark), and the baked model is the textured ground plus flat water for lakes and the sea
  (`BakeOptions::terrain_texture`, 1024 by default, 0 for the old flat surfaces). `assets::EncodePngRgb8` writes PNGs. The cook,
  the importer cache key and content moves now follow a `.glb`'s external images (they only did for `.gltf`).
- **Shorelines, a skirt and water you can see into.** Water runs on under the shore so the visible shoreline follows the ground's
  contour, and the terrain gets a skirt (`terrain_skirt`, 6 m by default) that carries its edges down so it reads as a block.
  Water carries a texture (`water_texture`, 512 by default): turquoise shallows to dark blue deep by real depth, with a lacy foam
  line along the shore, 30 percent opaque in the shallows to 93 in the deep. A ripple normal map (`RenderWaterNormalMap`) makes
  it catch the light, and the water's normal layers scroll with the game's time, so it moves.
- **Reflections, swells and whitecaps.** Water mirrors terrain, non-swaying objects, clouds and the sun (Vulkan;
  `AETHER_RENDER_REFLECTIONS=0` disables it). Its surface lifts and tilts with the wind as three travelling swells, and foams on
  the crests in a wind strength over about 0.7. A world with no Wind component gets the default breeze, so its water has a gentle
  swell; set the wind strength to 0 for flat water.
- **Collision and a player.** `terrain_collision` (on by default where the editor is built with physics; `terrain_collision_grid`
  sets how fine) adds a static triangle-mesh collider over the ground so a `CharacterMovement` capsule stands on and walks over a
  baked terrain. On HeroValley it adds 0.5 to 0.7 s to the player's start and about 8 MB to the source scene, and the mean gap
  between collision mesh and heightmap is 6 cm. `add_player` adds a Player on the Third Person template's controller, a small
  figure for a body, a camera, a sun and a sky, on dry gentle ground (`ProceduralWorldDocument::FindSpawnPoint`), plus invisible
  walls round the map's edge. `templates::InstallThirdPersonKit` writes the controller and bindings into any project (existing
  files kept). Bakes made before these options must be baked again.
- **A player that walks.** The third-person controller sweeps a sphere from the character's head toward the camera and keeps the
  camera in front of whatever it hits, coming in at once and easing back out (`camera_collision`, `camera_radius`, off-able; a
  build without physics keeps the old behaviour). The baked figure is a body and four limbs that swing with its pace
  (`Scripts/LimbSwing.luau` from `InstallThirdPersonKit`, usable by any jointed figure).
- **Tiles.** The baker cuts the ground into 8 by 8 primitives (`BakeOptions::terrain_tiles`; 1 keeps one piece) with
  `assets::procedural::SplitIntoTiles`, which copies the vertices on a cut with their normals so no seam shows. One primitive had
  one bounding sphere around the whole map, so neither the camera nor a shadow cascade could ever skip any of it. On a baked
  HeroValley the frame is 11 to 14 percent cheaper on the software rasterizer (the shadow pass 14 percent), with an identical
  picture.

Fixed: a basin under the sea that spilled lower than the sea had its own lower water level, leaving a band of ground standing out
of the sea. Its water now stands at the sea's level; worlds baked before this need a re-bake.

### Wind

A **`Wind` component** (direction in degrees about up, strength 0 to 4, gust speed, gustiness) sets the wind every swaying
material follows; the first in the world is used, a world without one keeps the old breeze. The direction is in the world
whatever way an object faces, and the sway is in world metres whatever its scale. New **`WindZone`** components (up to 7) are
spheres with their own wind that replace the world's inside them, fading over `falloff`.

A glTF material with the `AETHER_materials_wind` extension (metres of sway at the top, 0 to 0.3) sways in the vertex shader with
the game's time, weighted by height so roots stay put, with a phase from where each instance stands so a field moves like a gust.
The procedural generators set it on grass, reeds and shrub and tree leaves, and the scene shader's frame constants now carry the
game's time for effects like this. Shadows sway too: `ShadowCaster` and `ShadowCasterConstants` carry the sway, and wind-flagged
casters are drawn into the shadow cascades like skinned meshes (virtual shadow pages under them fall back to the cascades).
Baked scenes include a `Wind` entity (`BakeOptions::add_wind`, direction and strength; on by default). Plants take a small
per-instance colour tint from their world position, so forests and grass fields are not one colour.

## Rendering and the player

**Screen-space ambient occlusion.** The post pass darkens the HDR scene where the depth copy shows nearby surfaces closing in: 12
golden-angle taps in a 2.5 m sphere, normals rebuilt from depth, strength 0.9, before exposure and the tone mapper. It needs the
HDR path and the scene depth copy (the same one temporal anti-aliasing reads). `AETHER_RENDER_AO=0` turns it off;
`AETHER_RENDER_AO_STRENGTH` and `AETHER_RENDER_AO_RADIUS` tune it. Known limits: it darkens directly lit surfaces (it multiplies
the final colour), the noise is not blurred, and thin geometry does not occlude.

**Fog.** `PostProcessVolume::fog_density` (1 / m, default 0: off) fades the scene toward the sky's colour with distance from the
camera, `1 - exp(-density * distance)`, from the scene depth copy, blending between volumes like the other settings; the sky is
left alone. Fog also takes 10 percent of the sun's colour toward the sun (in-scatter; `AETHER_RENDER_FOG_SUN` changes the share).
`height_fog_density`, `height_fog_falloff` and `height_fog_base` add exponential height fog that pools in valleys and over water.
Transparent draws are not fogged (they are not in the depth copy).

**Clouds.** `SkyLight::cloud_coverage`, `cloud_scale` and `cloud_speed` draw procedural clouds lit by the sun and drifting with
the Wind (off by default), and `SkyPass::DrawMirrored` puts the sky and sun into the water's reflection.

**Drawing costs less.**

- The draw loop reads each entity's local transform once a frame instead of once for every drawn entity under it. For 10,000
  entities in a tree the transform work falls from about 2.0 ms to 1.3 ms a frame; scenes without hierarchies cost what they did.
  Transforms are bit for bit the same. `ExtractRenderScene` got the same treatment (5.7 ms to about 3 ms for 10,000 objects in a
  tree), and `HierarchySnapshot` is available to games that ask about many entities at once.
- The player built each drawn node's normal matrix by inverting its whole 4x4 transform, every frame. It now computes the inverse
  transpose of the linear part directly, about 40 times fewer instructions: recording a frame of 20,000 identical entities fell
  from 21.8 to 18.8 ms on the software Vulkan driver. Lighting is unchanged within rounding, and a 20,000-entity frame still
  costs more than a 60 Hz frame because each entity is its own draw call.
- The scene pass leaves out a draw whose bounding sphere is outside the camera's view or smaller than a quarter of a pixel
  (`player/src/view_cull.h`); skinned meshes, water, shadow casters and the water mirror's draws are unaffected. A baked
  HeroValley (6,001 draws) went from 266 to 156 ms a frame on the software rasterizer with identical output.
  `AETHER_RENDER_CULLING=0` turns it off.
- A shrub or tree of 100 or more triangles has a second, cheaper index list over the same vertices (`player/src/mesh_lod.h`),
  drawn and used for its cascade shadow when it is under 24 pixels in radius. The scene pass is about 7 percent cheaper in a
  plant-heavy view (frame -4 percent, not measured on a GPU; the picture changes in under 4 percent of its pixels).
  `AETHER_RENDER_LOD=0` turns it off.

**Render textures with depth.** `IDevice::CreateRenderTextureWithDepth` and `PipelineDesc::render_texture_depth` give a colour
render texture its own D32 depth attachment, cleared by every `BeginTexturePass`. Vulkan only for now; D3D12 returns an invalid
handle.

**A new glTF material extension.** `AETHER_materials_detail` (`strength` 0 to 1) adds a procedural micro-normal and brightness
variation from world position that fades with distance; procedural-world terrain uses it.

## 2D

**Packaged projects render Sprite2D content.** The player turns scene sprites and tilemap layers into the same textured quad
batches the renderer's particle pass uses, closing the gap where 2D template scenes loaded and simulated but drew nothing. Sprites
and tilemaps sample the Sprite2D light map when a scene contains enabled 2D lights: point, spot and global ambient lights affect
them, with tilemap occlusion and box shadow casters applied by the light map.

**`SpriteAnimator` works in packaged games.** No stage advanced it, so an animated sprite stayed on one frame. `Player.SpriteAnimation`
now runs each frame after scripts and Blueprints, reading sprite atlases from the package on first use: looping clips loop, a
non-looping clip stops on its last frame and sets `finished`, and a clip the atlas lacks leaves the sprite as it is.

**A character that falls out of the level can be put back.** `PlatformerController2D` has `respawn_on_fall` and `fall_limit_y`:
with the first set, a character that drops below the limit is put back where it stood on its first step, at rest (`respawns`
counts how often). It is off by default; the 2D Platformer template turns it on, since its level has a pit.

## Cooking, packaging and scenes

- **Cooked meshes are cached.** A cook that changed nothing still rebuilt every mesh's LODs and meshlets; they now go through
  the derived data cache like importer outputs and cooked textures, so a repeat cook of 1,000 models takes 3.9 s instead of 6.3 s
  (measured on Linux; the table is in `docs/design/PERFORMANCE.md`, "Cooking at scale"). `CookReport` gains `mesh_cache_hits` and
  `mesh_cache_misses`. The archive is byte for byte unchanged; delete `Intermediate/DerivedDataCache` to force a rebuild.
- **Archives are packed on several threads.** Writing an `.apak` checksums and compresses its entries on all of the machine's
  threads (up to 16), producing the same bytes. On 4 cores a repeat cook of 1,000 models takes 1.65 s instead of 3.9 s, and a
  first cook 4.7 s instead of 7.3 to 9.2 s. `PakWriter::SetThreads(1)` restores the serial path.
- **Textures are compressed on several threads.** BC1, BC3, BC4, BC5 and BC7 textures of 256x256 and up are block-compressed on
  all threads (up to 16), producing the same bytes, so caches stay valid. On 4 cores a 2048x2048 BC7 texture cooks in 1.8 s
  instead of 6.0 s. ASTC is unchanged; `TextureCookSettings::threads = 1` restores the serial path.
- **Large subtree operations are linear.** `Lifecycle::Destroy` and `MakePrefab` scanned the whole world once for every entity
  under the one they were given. They now find all children in one pass (`ChildIndex`, also available to games): destroying a
  20,000-entity subtree takes 5.7 ms instead of 238 ms, and 50,000 entities 12 ms instead of 1.7 s. A parent cycle in damaged
  data now ends instead of looping. `SubtreeOf` returns an entity and everything under it.
- **Scene saves keep a recoverable previous version.** Binary and JSON saves replace their target atomically and keep the prior
  file as `<scene>.bak`, so an interrupted save leaves the original intact. A new test kills a child process 100 times at random
  moments while it writes a scene and its autosave (about one in ten mid-write): the scene, the backup and the autosave are whole
  every time, and the same test against a non-atomic writer fails.

## Reliability and diagnostics

- **Import failures say what is wrong.** The model importer reports, in `ImportResult::warnings` (and the new
  `GltfScene::warnings`), every primitive it skipped and every attribute it dropped, naming the mesh, the primitive and the cause
  (a file with a bad primitive used to import as "ok" and empty). It refuses an index past the vertices, requires a glTF 2.x
  `asset.version`, and gives the JSON parser's line and column, "the file is empty", and which buffer file is missing. The
  texture importer says whether a file is a Git LFS pointer, an HTML page, a format it does not import (WebP, TIFF, DDS), text,
  or a truncated PNG, JPEG or BMP. A good file still says nothing.
- **A scene with an unknown component is refused by name, not stripped.** The MCP `load_scene` (and `aether_mcp_server --scene`)
  used to skip an unknown component with a log line, and a later `save_scene` deleted it from the file; they now refuse, naming
  each unknown component. `allow_unknown_components=true` loads the rest knowingly and returns `skipped_components` and a warning,
  and `SceneLoadOptions::unknown_components` collects the names for any caller. The editor's refusal names them too. Fixed: the
  editor renamed an old scene's unnamed entities again ("Entity 2" to "Entity 2 2") the second time the scene was opened.
- **Script errors say which entity and where, and do not flood.** A Luau error ends with the callback and the entity (`(in
  OnUpdate, on entity "Front Door" a0b1c2d3)`), so one broken script on forty doors can be told apart. The instruction-budget
  error for an endless loop names the file and line it was stuck on, like every other script error, and an error that repeats is
  one entry that counts its repeats (logged at 1, 10, 100 times and so on). `ScriptSystem::Errors()` keeps at most
  `kMaxDistinctErrors` (200); `DroppedErrors()` counts the rest.
- **The AI utility loader no longer crashes on malformed input.** Thirteen unchecked `json.value(key, default)` reads threw on a
  mismatched type (`{"actions":[{"name":5}]}` was enough), past the one place `GuardJsonLoader` could catch it, the same shape as
  the `StateTree::Validate` crash the fuzzer found. All thirteen now go through checked helpers, with a new `JsonFloat` in
  `core/json_util.h` and an explicit `is_array()` check before iterating considerations. All eight malformed documents are now
  tests.
- **Animation mistakes are diagnosed.** Invalid animation graph parameter commands, failed montage playback and unavailable
  montage-section jumps report the entity and request once per distinct problem, instead of failing silently or flooding the
  diagnostics list.
- **A new `HeightfieldCollider`** gives static terrain collision from a grid of heights (`samples` x `samples`, `cell_size`,
  `origin`) without a triangle mesh in the scene. The largest float (`kHole`) marks a hole; a grid that cannot be used is reported
  with the reason and gets no body.
- **AETHER-01's LastLight Valley renders.** `LastLight_Valley.bin` was 300,062 bytes where its glTF declares 330,324, so the
  environment failed to load and drew as nothing apart from one log line. It is regenerated by the game's own builder, whose
  river ribbon also faced down and is now wound up. `validate_assets.py`, which catches the length mismatch, now runs as the
  `aether01_assets_validate` check (nothing ran it before).

## Onboarding

`aether_new <Name> --template <id>` creates a project from a template without the editor (`aether_new --list` shows them) and
prints the two commands that package and run it. The First Person, Third Person, Top Down and Vehicle templates used to run to a
black window because they held no models: they now generate a floor, a player body and pickups from one cube in three colours,
and include a procedural sky light for environment background and ambient image-based lighting without an imported sky texture.
All six templates were created, packaged and run this way on Linux; Blank still opens on a dark window by design. The
getting-started page has the three commands.

`aether_plugin new <Name> [--dir <parent>] [--module]` creates a plugin folder without the editor. The scaffold (also what the
editor's Plugins window makes) used to declare a runtime module named after the plugin although it had no code, so enabling the
plugin produced "The module 'Coins' isn't built into this player" at every launch. It is content only now; `--module`, or
`CreatePluginScaffold(..., with_module = true)`, declares the module for a plugin that has code. A plugin scaffolded before this
keeps the module line in its `.aplugin`; delete it if the plugin has no code.

## Filming a run

`aether_player --camera-path <json> --record-dir <dir>` has the scene's camera follow keyframes and writes every frame (format in
`player/src/camera_path.h`). `--record-dir <dir> [--record-fps <n>] --frames <n>` writes the frames of a normal run at the film's
frame rate, so a scene's own sequences are filmed without a camera path; the two work together.

Fixed: `aether_player --press <Key>` set its keys once at start, and a window that loses the keyboard clears every held key
(which always happens under a virtual display), so windowed smoke runs had no input after their first frame. The keys are now set
again every frame, as "held for the whole run" says.

## The editor is Dear ImGui now

At the project owner's request the Qt editor (`editor/qt`, target `aether_editor_qt`, option `AETHER_BUILD_QT_EDITOR`) is gone,
and `aether_editor_shell` (Dear ImGui over Vulkan) is the editor. Removed with it: its `--self-test` ctest, its Windows packaging
and the Qt install steps in CI, the Qt coverage ledger and UX roadmap, and the Qt concept page. `aether_editor_core` and the
document classes stay (the ImGui panels and the MCP tools use them). Costs, stated plainly: the Windows package no longer contains
an editor, only the build tools, the player and the assets (the hosted Windows runner has no Vulkan loader), so the package
validation job checks that those are present instead of launching an editor.

The Qt editor had also been crashing at startup on its D3D12 renderer while CI stayed green, because the only automated check of it
ran `--self-test`, which never initialises the renderer. That defect is recorded rather than fixed: the editor that replaced it is
the ImGui shell.

## Installer

The application installer (`Aether-<version>-Windows-x64.exe`, built by `tools/build_installer.py`; source in
`tools/installer/AetherInstaller.cs`) was reworked after a report that it did not install and the old editor kept running:

- It closes any Aether program running from the install folder (asking first) and moves the previous installation aside before
  unpacking, all or nothing, so a file that is still open leaves the old installation intact rather than half deleted and the
  failure says so.
- It checks that the editor executable exists after unpacking, writes `INSTALLED_VERSION.txt`, creates "Aether Editor" shortcuts
  in the Start menu and on the Desktop, and offers to start the editor. Earlier installers made no shortcuts and started nothing,
  so anyone launching from an old shortcut or folder kept running the old build.
- The check now looks for `bin\aether_editor_shell.exe`, not the removed Qt `bin\aether_editor.exe` (one constant, `EditorExe`,
  used for the check, the shortcuts and the launch); every installer built since the Qt editor went had failed after unpacking
  with "the installation is incomplete". `build_installer.py` turns the Vulkan backend on explicitly, since the shell is only
  built with it.
- Run with no arguments it shows a setup wizard: a welcome page, the install folder (with Browse, and a note when an installation
  is already there or the drive is short of room) and checkboxes for the Start menu shortcut, the Desktop shortcut and starting
  the editor, a progress page (a bar and a log, the buttons off while files are written), and a finish page with "Start the Aether
  editor" (or the reason it failed and a way back). Enter continues; a running editor is closed only after asking. Unpacking now
  refuses a payload entry that would land outside the install folder. `/silent` installs with no window and writes to the
  console, and `/target:DIR`, `/noshortcuts` and `/nolaunch` pre-fill the window. One piece of code does the installing for both.
  The exe is a Windows program (`/target:winexe`) linking System.Windows.Forms and System.Drawing.

CI compiles the installer and runs it against a stand-in payload on Windows (`tools/installer/test_installer.ps1`: fresh install,
upgrade over a running program, a held file, shortcuts). Not covered: whether the editor it installs starts on a given machine.

The separate SDK installer that 0.29.0 published is gone: `tools/build_sdk_installer.py` became `tools/build_installer.py` and
builds the full application installer above. Its payload is the tree `cmake --install` stages, so it carries what a project
builds against as well as the editor and player, embedded as a managed resource compiled with `csc.exe` -- NSIS could not be
installed on the build machine, and `iexpress.exe` produced nothing usable. The application installer builds with Vulkan on,
because the editor shell is only built with it; the old SDK installer built with Vulkan off because the generated
`AetherConfig.cmake` requires the Vulkan SDK otherwise.

## Recorded, not fixed

The first run on the 0.29.0 tag failed two jobs: `Post-merge Linux (GCC)` on `bp/loop_arith_10k` at 3.25x and 3.20x against a
3.00x limit, and `Verify and record the editor screenshot` for a missing image. A re-run of the identical commit passed with zero
failures. So `bp/loop_arith_10k` (baseline 187 us) is unstable at roughly the 3x boundary on that runner and the benchmark gate
will intermittently fail on it. The noise floor does its job -- `cook/atex_roundtrip_256` no longer appears as a regression,
since its 1.8 us baseline is under the 0.01 ms floor -- but the floor does not cover a 187 us row that can triple. Raising the
tolerance to 4x would hide it, and raising the floor to 0.2 ms would stop gating everything under 200 us; the honest options are
a per-row tolerance or a baseline taken on the same runner, and both are bigger than a fix made at a tag.
